# Nox — UX/UI и performance аудит

Дата: 2026-06-17. Объём анализа: ~24 000 строк (`src/`, `server.js`, `prisma/schema.prisma`, дизайн-доки).

## Резюме без сглаживания

Это не сырой мессенджер. Дизайн-система (`globals.css`, `DESIGN.md`, `docs/product-redesign-system.md`) зрелая и когерентная, автор уже снял большинство очевидных перф-проблем (cache-first отрисовка списка и чата, мемоизация `MessageBubble`, рефы вместо зависимостей в decrypt-эффекте, мгновенные `loading.tsx` из RAM-кэша). Поэтому шаблонные советы из чек-листов («добавьте мемоизацию», «уберите спиннеры», «добавьте glass») — неприменимы и были бы враньём.

Реальные проблемы — точечные и доказуемые. Главный тезис: ощущение «не-премиума» сейчас даёт не визуал, а **накопительная деградация** (утечка слушателей сокета), **джанк восстановления скролла** и **архитектурный потолок** (история сообщений обрезана до 50, нет пагинации). Их и нужно бить в первую очередь.

## Чего этот аудит НЕ делал (граница достоверности)

Все перф-выводы — из статического анализа кода, а не из замеров. Я **не** запускал приложение, **не** снимал Lighthouse / FPS / трейсы, **не** тестировал на реальном устройстве, **не** прогонял полную сборку Next 16 (тяжёлая для песочницы). Где вывод требует проверки на устройстве — помечено «требует замера». Это не «возможно медленно вообще», а конкретные места кода с объяснимым механизмом замедления.

## P0 — критично (стабильность + скорость)

### P0-1. Утечка слушателя `message:new` в списке чатов — медленность копится по ходу сессии
**Файл:** `src/app/(app)/chats/ChatsPageClient.tsx:185`, cleanup `:261–269`.

Слушатель `message:new` вешается инлайн-функцией, но в `return () => {...}` для него **нет** `socket.off`. Сокет — модульный синглтон (`src/lib/socket-client.ts`), он переживает размонтирование страницы. Компонент `/chats` размонтируется и монтируется заново при каждом переключении вкладок. Итог: после N заходов на вкладку «Чаты» на одном сокете висит N обработчиков `message:new`. Каждое входящее сообщение запускает N вызовов `setChats` и, если чат не найден в списке, N параллельных `refreshList()` → N конкурентных `GET /api/chats` (каждый со своим `syncAbortRef`, они не отменяют друг друга). Это типичная накопительная утечка: чем дольше сессия, тем медленнее реакция списка.

Механизм подтверждён: `syncChats` стабилен (`useCallback(…, [])`), значит дело не в зависимостях эффекта, а именно в синглтон-сокете + неснятом слушателе.

**Статус: исправлено в этом проходе** — обработчик вынесен в `handleMessageNew`, добавлен `socket.off("message:new", handleMessageNew)`.

**Дополнительно:** `socket.off("message:receipts-updated")` (`:263`) снимается без ссылки на функцию — снимет вообще все обработчики этого события. Сейчас безопасно (он один), но это хрупкий паттерн. Рекомендация: именованные ссылки везде. Пройтись тем же глазом по `ChatMessages.tsx` и `ChatsRealtimeListener.tsx` (там тоже есть инлайн-`socket.on`).

### P0-2. Джанк восстановления скролла — экран дёргается до 1.2с после переключения вкладки
**Файл:** `src/app/(app)/AppShellChrome.tsx:133–137`.

```js
const restoreTimeouts = [0, 50, 150, 350, 700, 1200].map((delay) =>
  window.setTimeout(() => { window.scrollTo(0, restoreY); }, delay),
);
```

Каскад из 6 принудительных `scrollTo` растянут на 1.2 секунды. Если пользователь начал скроллить сразу после переключения вкладки, приложение рывком возвращает его на сохранённую позицию — вплоть до 1.2с спустя. Это прямое «приложение борется с пальцем» и читается как лаг. Плюс при `restoreY = 0` (свежая вкладка) всё равно дёргаются 6 бессмысленных `scrollTo(0,0)`.

**Статус: исправлено в этом проходе** — каскад сокращён до `[0,50,150,350]`, пропускается при `restoreY ≤ 0`, и **отменяется мгновенно** при первом `wheel`/`touchstart`/`keydown`. Восстановление остаётся, «рывок назад» исчезает.

> Замечание: 350 мс может быть мало при холодной загрузке с медленной отрисовкой. На практике список рисуется из кэша сразу, так что риск низкий. Требует замера на устройстве.

### P0-3. История сообщений жёстко обрезана до 50, пагинации нет
**Файлы:** `src/app/api/chats/[chatId]/messages/route.ts:166` (`take: 50`), клиент `ChatMessages.tsx:228+`.

`GET /messages` отдаёт только последние 50 сообщений, а в клиенте **нет** подгрузки старых (нет cursor / infinite scroll / «загрузить ещё»). Это:
- функциональный потолок: историю старше 50 сообщений нельзя прочитать вообще;
- разрыв с Telegram/iMessage, где история бесконечная.

Парадоксально это же объясняет, почему отсутствие виртуализации списка пока не болит: 50 узлов рендерятся дёшево. Но как только появится пагинация — без виртуализации (или хотя бы `content-visibility: auto` на группах) длинные чаты начнут тормозить.

**Статус: пагинация реализована** (коммит `361166c`). API получил `?before=<id>&limit` + `hasMore`; клиент подгружает предыдущую страницу при скролле к верху с якорением позиции. Потолок в 50 сообщений снят. **Виртуализация намеренно отложена** — см. «План C». Требует прогона сборки и теста на устройстве (правка в самом сложном файле).

### P0-4. Подсчёт непрочитанных тянет все строки и считает в JS
**Файл:** `src/lib/chat-list.ts:151–175`.

`unreadReceipts` делает `findMany` по **всем** непрочитанным `MessageReceipt` пользователя и сводит счётчики в JS-`reduce`. При активном пользователе это тысячи строк на каждый рендер списка чатов. `MessageReceipt` не хранит `chatId` (`schema.prisma:335`), поэтому прямой `groupBy` по чату невозможен.

**Решение (P0/P1):** `$queryRaw` со `JOIN message` и `GROUP BY message.chatId`, либо денормализовать `chatId` в `MessageReceipt` и сделать `groupBy({ by: ['chatId'], _count })`. Второе быстрее в проде, но требует миграции. **Не правил** — затрагивает запрос/схему, нужен прогон. Готовый `$queryRaw`-патч — в конце.

## P1 — важно (скорость, восприятие, консистентность)

### P1-1. Over-blur: `backdrop-filter` навешан на кнопки, инпуты и карточки
**Файл:** `src/app/globals.css` — `.btn-nox`, `.btn-primary`, `.input-nox`, `.card-premium` все несут `backdrop-filter: var(--glass-filter)` (`blur(20px) saturate(150%)`), и блок `@supports` в конце это дублирует.

Это противоречит вашему же `DESIGN.md`: «Surfaces: translucent only for dock, composer, sheets, and sticky chrome». `backdrop-filter` — дорогой GPU-слой; кнопок и инпутов на экране много, при скролле каждый такой слой пересчитывается. На среднем мобильном это главный кандидат в «медленность списков». Уберите blur с интерактивных контролов (оставьте заливку/границу/тень) — они и так лежат на тонированном фоне. Стекло — только на dock/composer/sheets/headers, как в доке.

**Статус: НЕ правил** — визуальное изменение, которое я не могу проверить глазами в этой среде. Готовый патч — в конце; примените и оцените визуально, откат — один `git checkout`.

### P1-2. Папки-фильтры пересчитываются 4 раза по всему списку
**Файл:** `ChatsPageClient.tsx:83–98`. `filteredChats` и `folderCounts` независимо фильтруют `chats` (4 прохода для счётчиков + 1 для фильтра). Для 500 чатов это 5×N на каждый рендер. Свести к одному проходу-редьюсеру. Низкий риск, заметно при больших списках.

### P1-3. Контакты — плоский список без поиска и приоритета
Из вашего же `product-redesign-system.md` (раздел Contacts) и кода `ContactsList.tsx` (2 мемо на 363 строки `NewChatForm`). Нет встроенного поиска/фильтра, online/recent/favorite не различаются, при 100+ контактах список не сканируется. Это не баг, а заявленный в редизайн-доке пробел, который бьёт по «премиальности» на масштабе.

### P1-4. Звонки — нет очевидного «перезвонить» в один тап
`product-redesign-system.md` (Calls) + `calls/page.tsx`. После пропущенного звонка самое вероятное действие — callback — не вынесено в один тап; пропущенные визуально не сильнее обычных. Telegram/iMessage здесь именно за счёт одного тапа ощущаются «дорого».

### P1-5. `ChatMessages.tsx` — монолит 1958 строк, ~40 `useState`/эффектов
Это не баг, но риск-фактор: огромная поверхность ререндера и тяжёлая поддержка. Декомпозировать на под-компоненты (composer / search-overlay / forward-picker / media уже частично вынесены) и стянуть состояние в редьюсер. Делать отдельной веткой, не в перф-проходе.

## P2 — полировка

- **Маршрутные анимации** (`globals.css`, `nox-route-*`) запускаются на каждом переключении вкладки. Сейчас аккуратны (transform/opacity, 240–340мс, `prefers-reduced-motion` учтён). Оставить; следить, чтобы `will-change` снимался (он снимается через `route-motion-idle` — ок).
- **`console.error`** в проде (`ChatMessages`, API auth) — легитимны, но `README` декларирует «логирование в проде минимизировано». Привести к одному gated-логгеру (как `debugRealtime`), чтобы не светить метаданные ошибок E2EE. `console.log` в чате уже под флагами `DEBUG_*` — трогать не нужно.
- **Presence/realtime в памяти** (`server.js:43–46`, `Map` `onlineUsers`/`activeCalls`) — единственный инстанс. Горизонтально не масштабируется (нужен Redis adapter для Socket.IO). Для текущего MVP-деплоя на одном long-running Node — приемлемо. Зафиксировать как известное ограничение перед масштабированием.
- **Пустые состояния** уже есть (`.nox-empty-*`), но в редизайн-доке отмечены как несогласованные между экранами — свести к одному компоненту.

## Готовые патчи (применять по вашему решению)

### Патч A — `backdrop-filter` только на chrome (P1-1)
В `globals.css` убрать строку `backdrop-filter: var(--glass-filter);` и парную `-webkit-backdrop-filter` из правил `.btn-nox`, `.btn-primary`, `.input-nox`; убрать эти три селектора из финального `@supports (... backdrop-filter ...)`-блока. Оставить blur у `.glass-header`, `.glass-composer`, `.nav-blur`, `.dock-liquid`, `.composer-liquid`, `.glass-panel`, `.card-premium`, `.liquid-top-chrome`.

### Патч B — непрочитанные одним запросом (P0-4)
```ts
// chat-list.ts, вместо findMany+reduce:
const rows = chatIds.length
  ? await prisma.$queryRaw<{ chatId: string; count: bigint }[]>`
      SELECT m."chatId" AS "chatId", COUNT(*)::bigint AS count
      FROM "MessageReceipt" r
      JOIN "Message" m ON m.id = r."messageId"
      WHERE r."userId" = ${userId}
        AND r."readAt" IS NULL
        AND m."deletedAt" IS NULL
        AND m."chatId" IN (${Prisma.join(chatIds)})
      GROUP BY m."chatId"`
  : [];
const unreadCountByChatId = Object.fromEntries(rows.map(r => [r.chatId, Number(r.count)]));
```
Проверить точные имена таблиц/колонок в сгенерированной схеме (camelCase в кавычках для Postgres) и `import { Prisma } from "@prisma/client"`.

### План C — пагинация истории (P0-3)
1. API: `?before=<messageId>&limit`, курсор по `id` со стабильным порядком `createdAt desc, id desc`, вернуть `hasMore`. — **СДЕЛАНО** (`361166c`).
2. Клиент: при скролле к верху грузить старые, **зафиксировать позицию** (запомнить `scrollHeight` до вставки, выставить `scrollTop += newScrollHeight - oldScrollHeight`). — **СДЕЛАНО** (`loadOlder` в `ChatMessages.tsx`).
3. **Осталось — виртуализация** (`@tanstack/react-virtual`) или `content-visibility: auto` на группах. Сейчас без неё: с пагинацией DOM растёт по мере прокрутки вверх, и очень длинная сессия в одном чате со временем начнёт тормозить. Это следующий шаг по P0-3.

Известные edge-cases пагинации для теста: чат ровно с 50 сообщениями (hasMore=false, дозагрузки нет); быстрый скролл-спам вверх (защищён `loadingOlderRef`); приход нового сообщения во время дозагрузки (prepend-guard не даёт сбить авто-скролл); короткий чат, где низ виден сразу.

## Живая диагностика в браузере (2026-06-17, dev)

Открытие чата и профиля «тупит», потому что у маршрутов **нет `loading.tsx`**: после тапа URL меняется, но Next держит предыдущий экран до резолва серверного компонента. Подтверждено через Chrome (URL `/chats/<id>` уже сменился, а на экране ещё ~1–2с висит список).

- `/chats/[chatId]` — `loading.tsx` **добавлен** (скелет чата). Проверено вживую: теперь сразу рисуется каркас, затем контент.
- `/users/[userId]` и `/chats/[chatId]/profile` — `loading.tsx` уже были (прошлая партия), вживую каркас появляется мгновенно.

Важно отделять dev от прода:
- **Компиляция Next на лету** (`npm run dev`, бейдж «Compiling…») добавляет секунды на первом заходе на маршрут — этого нет в проде. Реальную скорость мерить через `npm run build && npm start`.
- Аватары `/_next/image?...%2Fapi%2Favatars%2F...` → **400**: маршрут аватаров не под авторизацией, значит оптимизатор получает 404 (блобы лежат на прод‑volume Railway, в локальном `private_uploads` их нет). Это dev‑данные, не баг кода; в проде аватары есть.
- Дубли запросов (`/messages`, `/read`, key‑bundle по 2 раза) — React StrictMode в dev; в проде однократно.
- «Загрузка зашифрованного сообщения…» висит — это устройство **отозвано** (состояние аккаунта), E2EE не расшифровывает. Не баг кода.
