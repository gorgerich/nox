# Nox — звонки (WebRTC): почему не проходят между сетями и как починить

Дата анализа: 2026-06-17.

## Симптом

Аудио/видеозвонок работает, когда оба в «удобных» сетях, но **не устанавливается**, когда собеседники в разных сетях/городах — особенно если один на Wi‑Fi, а другой на мобильном интернете. Звонок висит на «Соединение…» и падает по таймауту.

## Диагноз (без догадок)

Это **не баг кода**. Код звонков (`src/app/(app)/calls/CallProvider.tsx`, функция `getRtcConfig`) написан корректно и уже умеет работать с TURN. Причина — **не поднят TURN‑сервер** и не заданы его переменные окружения, поэтому ICE работает в режиме «только STUN». Код сам это предупреждает в консоли:

> `[call-debug] TURN not configured; STUN-only may fail across NAT/mobile networks`

### Почему именно так

- **STUN** только сообщает клиенту его внешний IP:порт. Этого достаточно для «cone»‑NAT (обычные домашние роутеры).
- **Мобильный интернет** почти всегда за **CGNAT** (оператор прячет тысячи абонентов за одним IP), а многие роутеры дают **симметричный NAT**. В этих случаях STUN бесполезен — прямое соединение построить нельзя.
- Тогда нужен **TURN**: сервер‑посредник, через который идёт медиапоток, когда прямой путь невозможен. Без TURN пара «Wi‑Fi ↔ мобильный интернет в другом городе» почти гарантированно не соединится.
- Медиа остаётся зашифрованным (DTLS‑SRTP) даже через TURN — TURN ретранслирует уже зашифрованные пакеты и **не видит содержимого**, так что приватность звонка сохраняется.

### Отдельно для аудитории в РФ

Дефолтный STUN — гугловский (`stun.l.google.com`). В России он нестабилен/режется. Я добавил в дефолт Cloudflare и Twilio STUN для диверсификации, но **правильное решение — свой coturn** (он даёт и STUN, и TURN с одного своего сервера, стабильно в регионе).

## Что уже есть в коде

- STUN по умолчанию (Google + Cloudflare + Twilio), переопределяется `NEXT_PUBLIC_STUN_URLS`.
- TURN через env (`NEXT_PUBLIC_TURN_URL(S)` + username/credential).
- `NEXT_PUBLIC_FORCE_RELAY=true` — принудительный relay (для теста, что TURN реально работает).
- Встроенный дебаг‑оверлей в звонке показывает `TURN: YES/NO` и состояние ICE — по нему видно, подхватился ли TURN.

## Как починить — поднять TURN

### Переменные окружения (задать в `.env` / Railway Variables)

```
NEXT_PUBLIC_TURN_URLS=turn:turn.example.com:3478?transport=udp,turn:turn.example.com:3478?transport=tcp,turns:turn.example.com:5349?transport=tcp
NEXT_PUBLIC_TURN_USERNAME=<username>
NEXT_PUBLIC_TURN_CREDENTIAL=<password>
```

> **КРИТИЧНЫЙ НЮАНС.** Префикс `NEXT_PUBLIC_` означает, что значения **вшиваются в клиентский бандл на этапе `next build`**. Если задать переменные ПОСЛЕ сборки — они не подхватятся. Порядок такой:
> 1. Прописать переменные.
> 2. `npm run build` (уже с ними).
> 3. `NODE_ENV=production npm start`.
> На Railway: добавить Variables → передеплоить (пересобрать).

Указывайте сразу несколько транспортов: `udp` (основной), `tcp` (когда UDP режется), и `turns:` на **443/TLS** — последний пробивает строгие корпоративные/операторские файрволы, которые пропускают только HTTPS.

### Вариант A — managed TURN (быстро, 5–10 минут)

Провайдеры дают готовый TURN с креденшелами: **Metered (metered.ca)**, **Twilio Network Traversal**, **Cloudflare Calls (TURN)**, **Xirsys**. Регистрируетесь, берёте `urls/username/credential`, вставляете в env, пересобираете. Плюс — ноль администрирования; минус — трафик через них и лимиты бесплатного тарифа. Для РФ проверьте достижимость провайдера.

### Вариант B — свой coturn (контроль, лучший вариант для РФ)

На VPS (Ubuntu), у которого есть публичный IP и открыты порты 3478/5349 (UDP+TCP) и диапазон relay‑портов (напр. 49152–65535/UDP):

```bash
sudo apt-get install coturn
```

`/etc/turnserver.conf` (минимум):
```
listening-port=3478
tls-listening-port=5349
fingerprint
lt-cred-mech
realm=turn.example.com
# статичный пользователь (просто) ИЛИ time-limited секрет (безопаснее, см. ниже):
user=noxturn:ОЧЕНЬ_ДЛИННЫЙ_ПАРОЛЬ
external-ip=<ПУБЛИЧНЫЙ_IP_VPS>
min-port=49152
max-port=65535
# для turns: (TLS на 5349/443) — сертификаты Let's Encrypt:
cert=/etc/letsencrypt/live/turn.example.com/fullchain.pem
pkey=/etc/letsencrypt/live/turn.example.com/privkey.pem
```

Затем env как выше (`user:password` = `noxturn:...`). Проверить сервер снаружи: https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/ — ввести turn‑url + креды, должны появиться кандидаты типа `relay`.

## Как проверить, что помогло

1. Соберите с TURN‑переменными, запустите.
2. Позвоните между двумя реально разными сетями (Wi‑Fi ↔ мобильный).
3. В звонке дебаг‑оверлей должен показать `TURN: YES`.
4. Жёсткая проверка именно TURN: временно `NEXT_PUBLIC_FORCE_RELAY=true` (пересобрать) — если звонок при этом соединяется, значит TURN рабочий (форсируется relay‑путь). Потом верните `false`.

## Улучшения на будущее (делать с тестированием — звонки в песочнице проверить нельзя)

1. **Runtime‑эндпоинт ICE‑конфига вместо `NEXT_PUBLIC_`.** Сделать `GET /api/ice-servers`, который отдаёт `iceServers` из СЕРВЕРНЫХ env (без `NEXT_PUBLIC_`), и клиент запрашивает его перед созданием `RTCPeerConnection`. Плюсы: креды TURN не вшиваются в бандл, можно менять без пересборки, и можно выдавать **time-limited credentials** (coturn `use-auth-secret` + HMAC от timestamp) — это правильная практика безопасности TURN. Фолбэк на текущий env/STUN при ошибке.
2. **ICE‑restart при смене сети.** Сейчас при `iceConnectionState === "failed"` звонок сразу падает (`failCall`). Для мобильных (переход Wi‑Fi↔сота, смена вышки) стоит один раз попробовать `pc.restartIce()` + пере‑offer через сигналинг, прежде чем сбрасывать. Требует новых сигналинг‑событий на сервере (`server.js`) и аккуратного теста, чтобы не сломать рабочие звонки в одной сети.
3. **Разнести `connectionState`/`iceConnectionState` обработку `disconnected`** (транзиентное) от `failed` (терминальное) с коротким грейс‑периодом на восстановление.

Пункты 2–3 меняют сигналинг/поток звонка — их нельзя проверить в этой среде, поэтому они вынесены как отдельная задача «с тестами», а не слепая правка.
